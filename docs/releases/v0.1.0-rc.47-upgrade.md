# Runbook de upgrade — v0.1.0-rc.47

Upgrade hospitalar da `v0.1.0-rc.46` para a `v0.1.0-rc.47` (pendências
estruturadas e ordenação natural de leitos).

## Escopo

- `e13ed52`–`dabbe71` — pendências estruturadas internadas (change OpenSpec
  `structure-inpatient-pending-items`, PP-01 a PP-10 aceitos): catálogo
  categorizado (10 categorias, 46 entradas), cadastro estruturado com
  formulários progressivos por perfil, painel categorizado com filtros e
  histórico de classificação, exportação XLSX de 23 colunas (PP-08) e remoção
  do campo de busca por tipo (PP-10). Detalhes e evidências:
  `2026-11-08_v0.1.0-rc.47.md`.
- `9db0844` — `/beds` ordena leitos por ordem natural do identificador
  (chave extraída para `apps/census/bed_ordering.py`, aplicada a pacientes,
  linhas operacionais, linhas incompletas e legado; corrige a ordenação
  lexicográfica anterior).
- Sem mudanças em `compose.hospital.yml`, units systemd, scripts de deploy ou
  variáveis de ambiente.

## Impacto operacional

- Release de código **com migrations** em `pending_items`:
  `0003_catalog_category_and_classification` (categoria + metadados de
  classificação, anuláveis),
  `0004_load_pending_item_catalog` (carga do catálogo canônico),
  `0005_catalog_contract_constraints` (categoria obrigatória com `PROTECT`,
  perfis fixos, invariantes S1 no banco) e
  `0006_pending_item_details` (colunas de detalhes anuláveis + constraints).
  `migrate --noinput` **não é no-op** nesta release e deve aplicar exatamente
  essas 4 migrations de `pending_items` (nenhuma outra app).
- A carga `0004` é atômica e **adota tipos existentes somente por par exato
  slug+nome**. Tipos administrativos preexistentes fora do catálogo **não são
  excluídos**: são preservados e movidos para a categoria `Outras pendências`
  (`_preserve_legacy_types`). Se um tipo canônico tiver sido renomeado no
  hospital, a migration aborta com `CatalogLoadError` (diagnóstico contém
  apenas identificadores de catálogo, sem dados de pacientes) — nesse caso
  **pare e decida com o operador** antes de prosseguir.
- Revisões históricas de pendências são preservadas com metadados ausentes
  (colunas anuláveis expressam ausência histórica; sem parsing de texto e sem
  revisão fictícia — PI-10).
- UI pós-upgrade: páginas de pendências exibem categorias, formulários
  progressivos e filtros; exportação XLSX com 23 colunas; `/beds` em ordem
  natural de leito.
- Assets de runtime byte a byte idênticos aos das rc.34–rc.46 (Compose
  `cd0e444c…`). Nenhuma variável de ambiente, serviço ou timer novo.
- Rollback por imagem para a rc.46 (totalmente funcional): não desfaça as
  migrations nem restaure o banco — as colunas novas são anuláveis e ficam
  sem consumidor no código anterior; `PendingItemType.category` obrigatória
  não afeta a rc.46 porque tipos só são criados por migration, nunca em
  runtime. Dados estruturados capturados entre upgrade e rollback permanecem
  gravados, mas invisíveis na rc.46.

## Pré-condições

1. Confirmar versão atual `v0.1.0-rc.46` e PostgreSQL saudável.
2. Parar produtores e drenar até `drain_state=0 0`:

   ```bash
   systemctl stop sirhosp-stale-reconciliation.timer
   docker compose --env-file .env -f compose.hospital.yml stop census_orchestrator
   drain_state="$(
     docker compose --env-file .env -f compose.hospital.yml exec -T web \
       uv run --no-sync python -c \
       'import os,django; os.environ.setdefault("DJANGO_SETTINGS_MODULE","config.settings"); django.setup(); from apps.ingestion.models import IngestionRun,CensusExecutionBatch; print(IngestionRun.objects.filter(status__in=("queued","running")).count(), CensusExecutionBatch.objects.filter(status="running").count())'
   )"
   printf 'drain_state=%s\n' "$drain_state"
   test "$drain_state" = "0 0"
   ```

3. Baixar assets da release imutável rc.47 (Compose `cd0e444c…`).
4. Backup PostgreSQL custom + `pg_restore --list`.

## Download e backup

```bash
set -euo pipefail
export OLD_VERSION=v0.1.0-rc.46
export NEW_VERSION=v0.1.0-rc.47
export COMPOSE_FILE=compose.hospital.yml
cd /srv/apps/prisma
curl -fL --retry 3 -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"
curl -fL --retry 3 -o "${COMPOSE_FILE}.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${COMPOSE_FILE}"
for unit in sirhosp-discharges.service sirhosp-discharges.timer \
  sirhosp-historical-recovery.service sirhosp-historical-recovery.timer \
  sirhosp-stale-reconciliation.service sirhosp-stale-reconciliation.timer \
  sirhosp-daily-statistics.service sirhosp-daily-statistics.timer; do
  curl -fL --retry 3 -o "deploy/systemd/${unit}" \
    "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${unit}"
done
sha256sum "${COMPOSE_FILE}.new"   # cd0e444c…
cp -p "$COMPOSE_FILE" "${COMPOSE_FILE}.${OLD_VERSION}"
mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f $COMPOSE_FILE exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > "${backup_path}"
test -s "${backup_path}"
docker compose --env-file .env -f $COMPOSE_FILE exec -T db pg_restore --list < "${backup_path}" >/dev/null
echo "backup=${backup_path}"
```

## Upgrade

> `docker compose up -d` **sempre direto na linha de comando** (fora de
> heredoc) e com confirmação explícita das imagens.

```bash
umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${NEW_VERSION}/" .env > .env.new
grep -n "^SIRHOSP_VERSION=${NEW_VERSION}$" .env.new
chmod 600 .env.new && mv .env.new .env
mv ${COMPOSE_FILE}.new $COMPOSE_FILE
docker compose --env-file .env -f $COMPOSE_FILE config --quiet
docker compose --env-file .env -f $COMPOSE_FILE pull
docker compose --env-file .env -f $COMPOSE_FILE run --rm web \
  uv run --no-sync python manage.py migrate --noinput
```

Critério do `migrate`: exatamente
`pending_items.0003… OK`, `0004… OK`, `0005… OK`, `0006… OK` e nenhuma
outra migration. Se `0004` abortar com `CatalogLoadError`, não force: leia o
identificador do tipo divergente, decida com o operador (restaurar o nome
canônico ou coordenar ajuste) e repita o `migrate` — a carga é atômica, nada
parcial foi gravado.

Direto na linha de comando:

```bash
docker compose --env-file .env -f compose.hospital.yml up -d --remove-orphans \
  --scale persistent_worker=10 db web persistent_worker summary_worker
install -m 0644 deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
systemctl daemon-reload
docker compose --env-file .env -f compose.hospital.yml ps --format '{{.Name}} {{.Image}}' | sort
```

Critério: 12 containers na imagem rc.47 (web, summary_worker e 10
persistent_workers; o db permanece a imagem do PostgreSQL).

## Rollback

Somente imagem: a rc.46 está totalmente funcional. Não desfaça as migrations
`pending_items.0003`–`0006` nem restaure o banco; as colunas anuláveis
permanecem sem consumidor no código anterior e a categoria obrigatória de
`PendingItemType` não afeta a rc.46 (tipos só são criados por migration).
Pare produtores, drene, troque `SIRHOSP_VERSION=v0.1.0-rc.46` e recrie os
containers (mesmos passos acima; o `migrate` da rc.46 é no-op). Pendências
registradas com detalhes estruturados entre upgrade e rollback permanecem no
banco, mas a rc.46 não exibe os campos novos.
