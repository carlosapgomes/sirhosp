# SIRHOSP v0.1.0-rc.6 — Evidências e instruções de upgrade

## Status do artefato

Este documento acompanha a imagem e o `compose.hospital.yml` da release
imutável `v0.1.0-rc.6`. Ele descreve o upgrade a partir de `v0.1.0-rc.5`, mas
não autoriza sua execução. Backup, migration, ativação do catálogo e rollback
continuam sendo decisões explícitas do operador hospitalar.

## Resumo da release

A RC6 entrega:

- catálogo oficial de capacidade por setor, completo e versionado por data;
- medição imutável de ocupação para cada censo aceito;
- resumos diários com média aritmética de peso igual;
- capacidade, lotação registrada no legado, cobertura e alertas em `/beds`;
- defesa adicional contra processamento de censos incompletos;
- publicação de releases imutáveis no fluxo draft-first;
- documentação arquitetural na ADR-0003.

A release não ativa automaticamente o catálogo e não recalcula censos
anteriores. Até a ativação futura e o primeiro censo completo aplicável,
`/beds` permanece no fallback seguro.

## Valores esperados do catálogo inicial

O dry-run deve informar:

```text
grupos: 42
membros (códigos): 47
capacidade conhecida: 658
capacidade calculável: 626
```

Com os 47 códigos esperados observados, a medição deve registrar:

```text
setores com capacidade cadastrada: 44 de 47
setores com lotação calculável: 43 de 47
```

A Obstetrícia 3A conserva capacidade 32, mas permanece sem percentual até a
obtenção dos 16 pares cama-berço. Os leitos-dia continuam fora da taxa
hospitalar.

## Janela e responsáveis

Defina antes do upgrade:

- operador responsável;
- janela de manutenção;
- tag anterior e tag nova;
- caminho e checksum do backup;
- data futura de ativação em `America/Bahia`;
- critério objetivo de rollback;
- responsável pela validação funcional em `/beds`.

Não registre credenciais, tokens, cookies, nomes de pacientes ou conteúdo
clínico neste documento ou nos logs de evidência.

## Pré-flight no servidor hospitalar

Entre em `/opt/sirhosp` e preserve a versão anterior:

```bash
cd /opt/sirhosp
export OLD_VERSION=v0.1.0-rc.5
export NEW_VERSION=v0.1.0-rc.6
```

Confirme espaço, serviços e banco:

```bash
df -h /opt/sirhosp
docker compose --env-file .env -f compose.hospital.yml config --quiet
docker compose --env-file .env -f compose.hospital.yml up -d db
docker compose --env-file .env -f compose.hospital.yml ps
```

Confirme que a rede externa e o Cloudflared esperado estão presentes, sem
imprimir o `.env` ou o Compose interpolado:

```bash
docker network inspect hospital_edge --format '{{json .Containers}}'
```

Baixe o Compose pertencente à mesma release para um arquivo temporário:

```bash
curl -fL \
  -o compose.hospital.yml.rc6 \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/compose.hospital.yml"
```

Valide-o com as variáveis atuais:

```bash
docker compose --env-file .env -f compose.hospital.yml.rc6 config --quiet
```

## Backup obrigatório

Crie um backup PostgreSQL antes de migration ou troca de imagem:

```bash
mkdir -p backups
chmod 700 backups
export BACKUP_FILE="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f compose.hospital.yml exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "${BACKUP_FILE}"
test -s "${BACKUP_FILE}"
sha256sum "${BACKUP_FILE}" > "${BACKUP_FILE}.sha256"
chmod 600 "${BACKUP_FILE}" "${BACKUP_FILE}.sha256"
```

Guarde o backup fora do diretório público e não o envie ao repositório ou ao
GitHub.

## Selecionar a RC6

Substitua o Compose somente depois de validá-lo:

```bash
mv compose.hospital.yml compose.hospital.yml.rc5
mv compose.hospital.yml.rc6 compose.hospital.yml
```

Edite somente `SIRHOSP_VERSION` no `.env` local:

```text
SIRHOSP_VERSION=v0.1.0-rc.6
```

Não imprima o `.env`. Confirme apenas a configuração:

```bash
docker compose --env-file .env -f compose.hospital.yml config --quiet
```

## Pull e migrations

Baixe a imagem exata e mantenha o banco saudável:

```bash
docker compose --env-file .env -f compose.hospital.yml pull
docker compose --env-file .env -f compose.hospital.yml up -d db
```

Aplique migrations com um container one-shot da RC6:

```bash
docker compose --env-file .env -f compose.hospital.yml run --rm web \
  uv run --no-sync python manage.py migrate --noinput
```

Verifique que as migrations census 0014 a 0017 aparecem aplicadas, sem exibir
configuração sensível:

```bash
docker compose --env-file .env -f compose.hospital.yml run --rm web \
  uv run --no-sync python manage.py showmigrations census
```

## Subir a aplicação

```bash
docker compose --env-file .env -f compose.hospital.yml \
  up -d --remove-orphans
```

Reaplique explicitamente a escala operacional aprovada. O exemplo abaixo usa
15 réplicas, mas o operador deve manter a quantidade validada para o hospital:

```bash
docker compose --env-file .env -f compose.hospital.yml \
  up -d --scale persistent_worker=15 persistent_worker
```

Verifique serviços e saúde:

```bash
docker compose --env-file .env -f compose.hospital.yml ps
curl -fsS http://127.0.0.1:8000/health/
docker compose --env-file .env -f compose.hospital.yml \
  logs --tail 200 web census_orchestrator persistent_worker summary_worker
```

Antes da ativação, `/beds` deve continuar funcional com fallback e sem
percentual inventado.

## Validar o catálogo sem persistir

Escolha explicitamente uma data estritamente futura em `America/Bahia`. Não use
a data do servidor sem confirmar o timezone institucional:

```bash
TZ=America/Bahia date
export EFFECTIVE_FROM=YYYY-MM-DD
```

Execute o dry-run:

```bash
docker compose --env-file .env -f compose.hospital.yml run --rm web \
  uv run --no-sync python manage.py activate_sector_capacity_catalog \
  --input apps/census/data/initial_sector_capacity_catalog.json \
  --effective-from "${EFFECTIVE_FROM}" \
  --dry-run
```

Pare sem ativar se os totais não forem exatamente 42, 47, 658 e 626, se o hash
não aparecer, se a data não for futura ou se houver conflito de catálogo.

## Ativação controlada

A ativação é uma ação separada do upgrade. Execute somente com aprovação
operacional registrada e após o dry-run aprovado:

```bash
docker compose --env-file .env -f compose.hospital.yml run --rm web \
  uv run --no-sync python manage.py activate_sector_capacity_catalog \
  --input apps/census/data/initial_sector_capacity_catalog.json \
  --effective-from "${EFFECTIVE_FROM}"
```

A repetição com a mesma data e documento é idempotente. Não publique outro
conteúdo para a mesma data. Correções futuras exigem uma nova fotografia
completa e uma nova data futura.

Não execute `materialize_occupancy_measurement` para censos anteriores. A série
oficial começa no primeiro censo completo e aceito aplicável após a ativação.

## Validação após a data efetiva

Após o primeiro censo completo e aceito da data efetiva:

1. confirme `/health/`;
2. abra `/beds` com usuário autorizado;
3. confirme o rótulo `Lotação registrada no sistema legado`;
4. confira capacidade conhecida 658 e calculável 626;
5. confira cobertura 44/47 e 43/47 quando os 47 códigos forem observados;
6. confirme 3A com capacidade 32 e cálculo pendente;
7. confirme setores sem capacidade e desconhecidos explícitos;
8. confira alertas acima de 100% e o excedente absoluto;
9. monitore `unmapped` e nomes divergentes;
10. confirme ausência de erros estruturais antes de efeitos clínicos.

Coberturas podem ser menores se o censo legítimo contiver códigos novos ou não
observar todos os 47 esperados. Isso deve gerar investigação, não remapeamento
ou capacidade automática.

Inspecione logs agregados, sem copiar dados de pacientes:

```bash
docker compose --env-file .env -f compose.hospital.yml \
  logs --since 30m web census_orchestrator
```

## Critérios de rollback

Considere rollback da aplicação se ocorrer:

- falha persistente de health check;
- migrations não concluídas;
- erro estrutural repetido antes do processamento clínico;
- indisponibilidade de `/beds` ou regressão de autenticação;
- instabilidade operacional não corrigível na janela.

Um setor `unmapped`, uma divergência de nome ou percentual extremo isolado não
justifica apagar histórico. Esses são estados auditáveis e devem ser
investigados.

## Rollback funcional para RC5

As migrations 0014 a 0017 são aditivas. Para retornar a aplicação, mantenha as
tabelas e dados novos, altere `SIRHOSP_VERSION` para a tag anterior e restaure o
Compose correspondente:

```text
SIRHOSP_VERSION=v0.1.0-rc.5
```

```bash
mv compose.hospital.yml compose.hospital.yml.rc6
test -f compose.hospital.yml.rc5
mv compose.hospital.yml.rc5 compose.hospital.yml
docker compose --env-file .env -f compose.hospital.yml config --quiet
docker compose --env-file .env -f compose.hospital.yml pull
docker compose --env-file .env -f compose.hospital.yml \
  up -d --remove-orphans
docker compose --env-file .env -f compose.hospital.yml \
  up -d --scale persistent_worker=15 persistent_worker
docker compose --env-file .env -f compose.hospital.yml ps
curl -fsS http://127.0.0.1:8000/health/
```

Não reverta migrations, não exclua versões, medições ou resumos e não use
`docker compose down -v`. Se houver dano de banco ou incompatibilidade não
prevista, pare os serviços mutantes e execute restauração coordenada do backup,
seguindo o procedimento institucional.

Uma ativação já publicada permanece como evidência. O rollback da aplicação
apenas interrompe a materialização/UI nova; não autoriza editar ou apagar o
passado.

## Pós-deploy

Monitore por pelo menos um ciclo completo de censo e registre apenas evidências
agregadas:

- status dos containers;
- health check;
- sucesso/falha do censo;
- criação da primeira medição aplicável;
- coberturas de capacidade e cálculo;
- quantidade de códigos `unmapped` e divergências de nome;
- alertas de lotação acima de 100%;
- decisão de manter RC6 ou executar rollback.

## Itens deliberadamente não resolvidos

- Os 16 pares cama-berço da Obstetrícia 3A ainda são desconhecidos.
- Leitos-dia ainda não possuem indicador próprio.
- Não há UI histórica para medições e resumos.
- O limiar de completude continua fixo em 40 setores.

Esses itens não bloqueiam a RC6 e não devem ser improvisados durante o upgrade.
