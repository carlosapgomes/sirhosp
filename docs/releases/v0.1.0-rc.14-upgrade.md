# SIRHOSP v0.1.0-rc.14 — Caracterização da coorte fail-only de full-sync (CFC)

## Status do artefato

Este é o runbook de pré-publicação da candidata `v0.1.0-rc.14`. Ele somente se
torna um asset operacional válido quando anexado, antes da publicação, à
release GitHub imutável da mesma tag e quando a imagem exata existir no GHCR.

O upgrade parte de `v0.1.0-rc.13` (em produção desde 2026-08-28). Esta release
entrega o ferramental **diagnóstico read-only** do change
`characterize-fullsync-chronic-failures` (CFC): o command de caracterização
da coorte fail-only, o gerador de relatório com validador da ADR de decisão, o
harness de laboratório sintético (isolado em `automation/lab/`) e a ADR-0008
preenchida. Sem migration, sem catálogo, sem dependência nova e sem qualquer
comando de mutação — o `migrate` é executado apenas por idempotência e deve
resultar em `No migrations to apply`.

Nenhuma correção da coorte é implementada nesta release: a ADR-0008 confirmou
as causas (H1 deadline por volume; H2 payload determinístico) e a correção é
objeto do change futuro `fix-fullsync-failure-exhaustion` (proposta apenas,
sem implementação). Nenhum `--apply`, reprocessamento ou reenfileiramento é
executado durante o upgrade.

O critério central desta release é o fechamento do R1 do CFC-S4: executar o
one-shot de caracterização **em produção** (janela 7d), fechando a pendência
operacional registrada na verificação do slice (a imagem `v0.1.0-rc.13` não
contém o command).

## Resumo da release

A RC14 entrega o change OpenSpec `characterize-fullsync-chronic-failures`
(slices CFC-S1 a CFC-S4, ativo — arquivamento é etapa pós-deploy, após o
one-shot fechar o critério R1):

- **S1** — command `characterize_fullsync_failures`: caracterização agregada
  read-only da coorte fail-only de `full_sync`/`full_admission_sync`
  (`--window-hours`, `--min-attempts`, `--max-per-stage-rows`); coorte,
  distribuição de reasons coorte/contraste, timing por estágio
  (mediana/p90), estágio terminal falho e histograma horário; chaves de
  paciente apenas em memória efêmera; exit 0 sempre que a caracterização
  completa (diagnóstico, não gate);
- **S2** — harness de laboratório `automation/lab/playwright_experiments/
  fullsync_failure_lab.py`: reprodução sintética das hipóteses H1 (timeout
  por volume/deadline) e H2 (invalid_payload por conteúdo) contra o código
  real de extração e classificação, com fakes duck-typed, fixtures 100%
  sintéticas versionadas e artefato `verdicts.json`; nunca importado por
  `apps/`;
- **S3** — command `generate_fullsync_failure_report`: relatório Markdown
  de cinco seções a partir da captura do S1, fail-closed em sentinela de
  identidade; validador objetivo da ADR de decisão (veredito com evidência,
  recomendação coerente, zero identidade); runbook operacional em
  `deploy/README.md` §6.2;
- **S4** — ADR-0008 preenchida (H1/H2 `confirmed` com evidência de
  laboratório + agregados de produção de 2026-08-28: coorte de 19 pacientes,
  588 tentativas esgotadas, `timeout`=372, `invalid_payload`=216, contraste
  233/252), índice de ADRs atualizado e proposição do change de correção
  `fix-fullsync-failure-exhaustion` (gitignored, não embarcado na imagem).

Também compõem a release, sem impacto de runtime: os commits de documentação
da RC13 (`e9a8556` evidence pack, `fb6f41a` evidência de deploy).

A release não altera schema, catálogos, medições, resumos, autenticação,
workers, orquestrador ou a topologia de produção. Todo o código novo é
aditivo e diagnóstico. Não há backfill, ativação ou ensaio de execução. Runs
históricos não são reabertos nem reenfileirados.

## One-shot CFC em produção (critério central desta release)

Após o primeiro ciclo natural de censo pós-deploy (confirme pelo menos um
batch concluído nos agregados do preflight/fluxo natural), execute a
caracterização da coorte fail-only conforme `deploy/README.md` §6.2.1:

1. Confirme a disponibilidade do command (novo nesta imagem):

   ```bash
   docker compose --env-file .env -f compose.hospital.yml exec -T web \
     uv run --no-sync python manage.py help \
     characterize_fullsync_failures >/dev/null && echo AVAILABLE
   ```

2. Registre contagens agregadas antes (evidência informativa; o contrato
   read-only é provado pela suíte unit do CFC-S1 com spies e contagens —
   em produção os workers continuam ativos e contagens podem divergir
   organicamente pela atividade do pipeline):

   ```bash
   docker compose --env-file .env -f compose.hospital.yml exec -T web \
     uv run --no-sync python manage.py shell -c \
     'from apps.ingestion.models import IngestionRun, IngestionRunAttempt, IngestionRunStageMetric, FinalRunFailure; print("CFC_BEFORE", IngestionRun.objects.count(), IngestionRunAttempt.objects.count(), IngestionRunStageMetric.objects.count(), FinalRunFailure.objects.count())'
   ```

3. Execute a caracterização (janela 7d, saída para arquivo no host; saída
   100% agregada, sem identidade — pública por construção):

   ```bash
   docker compose --env-file .env -f compose.hospital.yml exec -T web \
     uv run --no-sync python manage.py characterize_fullsync_failures \
     --window-hours 168 --min-attempts 3 \
     > /tmp/cfc-characterization.txt
   echo "CFC_EXIT=$?"
   cat /tmp/cfc-characterization.txt
   ```

   Esperado: `CFC_EXIT=0`. Interprete: `cohort:` deve guardar coerência com
   os agregados registrados de 2026-08-28 (coorte na casa de dezenas de
   pacientes, 588 tentativas, `timeout` dominante seguido de
   `invalid_payload`), com deslocamento natural da janela deslizante de 7
   dias. Desvio de ordem de grandeza não é falha do upgrade (é
   diagnóstico), mas deve ser registrado.

4. Gere o relatório e valide a ADR-0008 dentro do container (a ADR viaja
   na imagem em `docs/adr/`; o input precisa estar dentro do container):

   ```bash
   docker compose --env-file .env -f compose.hospital.yml cp \
     /tmp/cfc-characterization.txt web:/tmp/cfc-characterization.txt
   docker compose --env-file .env -f compose.hospital.yml exec -T web \
     uv run --no-sync python manage.py generate_fullsync_failure_report \
     --input /tmp/cfc-characterization.txt \
     --output /tmp/cfc-characterization-report.md \
     --check-adr docs/adr/ADR-0008-fullsync-failure-characterization-decision.md
   docker compose --env-file .env -f compose.hospital.yml exec -T web \
     cat /tmp/cfc-characterization-report.md
   ```

   Esperado: `report written` e `decision ADR valid` (exit 0).

5. Registre contagens agregadas depois (mesma ressalva orgânica do passo
   2) e confira a saída sanitizada (nenhum identificador, URL, texto
   clínico ou erro bruto — por construção e pelo scanner do gerador).

Não imprima, copie ou registre qualquer linha individual de run, paciente
ou internação; somente os agregados acima.

## Fluxo natural pós-deploy

Com orquestrador e dez workers restaurados, o pipeline retoma o ciclo
natural. Reexecute o agregado do preflight em intervalos regulares nas
primeiras horas e confira:

- fila drenando (`ingestion_queued`/`ingestion_running` → 0 entre ciclos);
- `full_sync` terminais e evoluções sendo criadas normalmente;
- `baseline_24h.admissions_succeeded_seen_zero = 0` mantido;
- orquestrador vivo (confirme o processo ativo em `ps`).

O canário do §6.1.2 (systemd timer do health check, sem provider de
alerta) continua recomendado conforme a RC13; a caracterização CFC
(§6.2.1) fica disponível sob demanda a partir desta release.

## Rollback trivial

A RC14 não muda schema nem escreve dados clínicos novos: o rollback é um
redeploy da RC13 já preservada:

1. pare serviços mutantes na ordem segura (`census_orchestrator web`, drene,
   depois `persistent_worker summary_worker`), com drenagem completa da
   fila antes de reverter;
2. restaure `compose.hospital.yml.rc13` sobre `compose.hospital.yml`;
3. selecione `SIRHOSP_VERSION=v0.1.0-rc.13` no `.env` sem imprimi-lo;
4. `config --quiet`, `pull` e retome a topologia com dez workers;
5. confirme health, revisão e catálogo v5 idêntico.

Nota: o rollback remove os commands CFC (diagnóstico apenas) — nenhum dado
é afetado. Não reverta migrations nem restaure backup para rollback
funcional; o backup existe para incidentes que exijam restauração
coordenada.
