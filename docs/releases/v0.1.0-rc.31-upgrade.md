# Runbook de Upgrade — v0.1.0-rc.31 (2026-09-26)

## Escopo

Esta release entrega o relatório estatístico diário nominal e os controles para
uma ativação operacional futura, além da estabilização dos testes de altas por
dia operacional:

- nova rota autorizada `/statistics/`, com seleção determinística do último dia
  pronto, relatório materializado e versionado por setor, fotografia final,
  entradas, transferências, óbitos e altas;
- permissões dedicadas `view_daily_statistics` e
  `export_daily_statistics`;
- export XLSX em memória, auditado após a resposta estar pronta, sem persistir
  o workbook;
- management command `materialize_daily_statistics`, com finalização automática
  limitada a datas fechadas iguais ou posteriores à data de ativação;
- assets futuros de runtime
  `sirhosp-daily-statistics.service` e
  `sirhosp-daily-statistics.timer`, publicados **desabilitados**;
- preflight host-level somente leitura
  `daily-statistics-activation-preflight.sh`, também anexado à release;
- correção exclusivamente de testes para remover dependência do relógio de
  parede em dois cenários de altas.

Base do upgrade: **v0.1.0-rc.30** (`8613e3d`).

O intervalo `v0.1.0-rc.30..HEAD` adiciona o app `statistics_reports`, cinco
migrations (`0001` a `0005`), a página e o export, os assets de runtime e os
respectivos contratos. `pyproject.toml`, `uv.lock` e `compose.hospital.yml`
permanecem inalterados. SHA-256 do Compose:
`a0076bed1b0046d430e88426977d7ea825d7e880d233faf088d6678da43123cd`.

Validação anterior à tag:

- **3.723** testes unitários;
- **885** testes de integração;
- Django check sem issues;
- Ruff aprovado;
- mypy sem issues em 445 arquivos;
- Markdown lint sem erros;
- OpenSpec strict válido.

## Limite operacional desta release

A publicação e o upgrade da imagem **não ativam** a finalização diária.
Instalação dos units, preflight, aceite humano e ativação são checkpoints
separados, descritos na seção 5c de `deploy/README.md`.

Durante este upgrade:

- não instale nem habilite `sirhosp-daily-statistics.timer`;
- não configure `STATISTICS_ACTIVATION_DATE`;
- não execute backfill, extração ou materialização manual;
- não simule marcadores de journal ou cadências upstream;
- não trate a disponibilidade dos assets como autorização para ativação.

A página pode permanecer sem dias prontos até uma ativação futura aprovada. Isso
é o comportamento esperado e não deve ser contornado.

## Impacto operacional

- Cinco migrations criam somente as tabelas e permissões do novo app de
  estatísticas. Não alteram tabelas clínicas existentes.
- Nenhuma dependência, imagem base, variável obrigatória do portal ou serviço do
  Compose foi adicionada.
- O runtime diário é externo ao Compose e permanece ausente ou desabilitado.
- Não existe backfill anterior à data de ativação futura.
- O rollback de imagem não exige desfazer migrations: as tabelas novas podem
  permanecer inertes e são ignoradas pela RC30.

## Pré-condições

1. Confirmar que a versão atual é `v0.1.0-rc.30` sem imprimir outras variáveis
   do `.env`.
2. Confirmar PostgreSQL saudável.
3. Registrar a escala atual de `persistent_worker`; o baseline hospitalar é de
   10 réplicas.
4. Parar temporariamente os produtores de novos ciclos, mantendo os workers
   ativos para drenar a fila.
5. Aguardar `IngestionRun` sem itens `queued` ou `running` e nenhum batch de
   censo aberto.
6. Baixar da release imutável o Compose e este runbook.
7. Criar backup PostgreSQL em formato custom, confirmar arquivo não vazio e
   validar seu catálogo com `pg_restore --list`.
8. Confirmar que o timer diário não está ativo nem habilitado, caso seus units
   tenham sido instalados anteriormente.

## Pausa e drenagem

No host hospitalar, como operador autorizado, em `/srv/apps/prisma`:

```bash
export OLD_VERSION=v0.1.0-rc.30
export NEW_VERSION=v0.1.0-rc.31
export COMPOSE_FILE=compose.hospital.yml

systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f "$COMPOSE_FILE" stop census_orchestrator
```

Confirme a drenagem antes de recriar os workers:

```bash
drain_state="$(
  docker compose --env-file .env -f "$COMPOSE_FILE" exec -T web \
    uv run --no-sync python -c \
    'import os,django; os.environ.setdefault("DJANGO_SETTINGS_MODULE","config.settings"); django.setup(); from apps.ingestion.models import IngestionRun,CensusExecutionBatch; print(IngestionRun.objects.filter(status__in=("queued","running")).count(), CensusExecutionBatch.objects.filter(status="running").count())'
)"
printf 'drain_state=%s\n' "$drain_state"
test "$drain_state" = "0 0"
```

Se houver itens ativos, aguarde com os workers em execução. Não reinicie
containers durante a drenagem.

## Download e backup

```bash
curl -fL --retry 3 \
  -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"
curl -fL --retry 3 \
  -o compose.hospital.yml.new \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/compose.hospital.yml"

cp -p "$COMPOSE_FILE" "${COMPOSE_FILE}.${OLD_VERSION}"
mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

mkdir -p backups
chmod 700 backups
backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "$backup_path"
test -s "$backup_path"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  pg_restore --list < "$backup_path" >/dev/null
printf 'backup=%s bytes=%s validated=1\n' \
  "$backup_path" "$(stat -c %s "$backup_path")"
```

## Upgrade

Não adicione `STATISTICS_ACTIVATION_DATE` neste procedimento.

```bash
umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${NEW_VERSION}/" .env > .env.new
chmod 600 .env.new
mv .env.new .env
mv compose.hospital.yml.new "$COMPOSE_FILE"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" run --rm web \
  uv run --no-sync python manage.py migrate --noinput

docker compose --env-file .env -f "$COMPOSE_FILE" \
  up -d --remove-orphans --scale persistent_worker=10 \
  db web persistent_worker summary_worker
```

O `migrate` deve aplicar `statistics_reports.0001` a
`statistics_reports.0005`. O orquestrador permanece parado durante os primeiros
smokes.

```bash
docker compose --env-file .env -f "$COMPOSE_FILE" ps
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T web \
  uv run --no-sync python manage.py check

docker compose --env-file .env -f "$COMPOSE_FILE" exec -T web \
  uv run --no-sync python manage.py showmigrations statistics_reports

docker compose --env-file .env -f "$COMPOSE_FILE" exec -T web \
  uv run --no-sync python manage.py shell -c \
  'from django.contrib.auth.models import Permission; print(Permission.objects.filter(codename__in=("view_daily_statistics","export_daily_statistics")).count())'

health_host="$(
  grep -E '^DJANGO_ALLOWED_HOSTS=' .env | cut -d= -f2- | cut -d, -f1
)"
host_port="$(grep -E '^DJANGO_PORT=' .env | cut -d= -f2-)"
test -n "$health_host"
test -n "$host_port"

curl -fsS -H "Host: $health_host" \
  "http://127.0.0.1:${host_port}/health/"
for path in painel/ painel/altas/ altas/ reconciliacao/ censo/ statistics/; do
  code="$(
    curl -sS -o /dev/null -w '%{http_code}' -H "Host: $health_host" \
      "http://127.0.0.1:${host_port}/${path}"
  )"
  printf '%s http=%s\n' "$path" "$code"
  test "$code" = "302"
done

if systemctl is-enabled --quiet sirhosp-daily-statistics.timer 2>/dev/null; then
  echo "daily statistics timer must remain disabled" >&2
  exit 1
fi
if systemctl is-active --quiet sirhosp-daily-statistics.timer 2>/dev/null; then
  echo "daily statistics timer must remain inactive" >&2
  exit 1
fi
printf 'daily_statistics_timer=disabled,inactive\n'
```

Critérios de aceite antes da retomada:

- web saudável e `/health/` responde com sucesso;
- cinco migrations de `statistics_reports` aparecem aplicadas;
- a consulta agregada de permissões imprime `2`;
- rotas autenticadas redirecionam usuário anônimo para login, incluindo
  `/statistics/`;
- usuários sem `view_daily_statistics` continuam sem acesso ao relatório;
- 10 réplicas de `persistent_worker` estão ativas;
- web e workers usam a tag exata `v0.1.0-rc.31`;
- `sirhosp-daily-statistics.timer` não está ativo nem habilitado;
- containers não estão em crash loop.

Atribua as permissões somente aos grupos aprovados pela administração. Não
registre nomes, prontuários ou conteúdo do relatório no terminal ou no ticket de
deploy.

## Ativação futura das estatísticas

Somente após decisão humana separada:

1. baixar da **mesma tag exata** o preflight e os dois units diários;
2. instalar os units em estado desabilitado;
3. configurar uma `STATISTICS_ACTIVATION_DATE` estritamente futura;
4. executar o preflight host-level e preservar somente sua evidência técnica
   agregada;
5. obter aceite humano explícito enquanto a evidência estiver fresca;
6. revalidar as cadências upstream e só então habilitar o timer.

Siga literalmente a seção 5c de `deploy/README.md`. Um resultado de preflight
`PASS` é pré-condição, não autorização automática.

## Rollback

O rollback retorna a imagem e o Compose à RC30. Não reverta as migrations de
`statistics_reports` durante o rollback rotineiro: a RC30 ignora essas tabelas e
a reversão destrutiva não é necessária.

Pare produtores e drene novamente a fila se eles já tiverem sido retomados.

```bash
export OLD_VERSION=v0.1.0-rc.30
export COMPOSE_FILE=compose.hospital.yml

systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f "$COMPOSE_FILE" stop census_orchestrator

umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${OLD_VERSION}/" .env \
  > .env.rollback
chmod 600 .env.rollback
mv .env.rollback .env
cp "${COMPOSE_FILE}.${OLD_VERSION}" "$COMPOSE_FILE"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" \
  up -d --remove-orphans --scale persistent_worker=10 \
  db web persistent_worker summary_worker
```

Valide a RC30 antes de reativar o orquestrador e o timer de reconciliação. O
backup PostgreSQL é uma salvaguarda operacional e não deve ser restaurado neste
rollback sem investigação e decisão específicas. O timer diário de estatísticas
deve continuar desabilitado.
