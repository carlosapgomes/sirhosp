# Runbook de Upgrade — v0.1.0-rc.30 (2026-09-22)

## Escopo

Entrega o change `rename-enf-2b-card-display-name` (3 slices verticais
RCD-S1/RCD-S2/RCD-S3, revisão independente por reviewer de contexto fresh:
`OK with notes` / `OK with notes` / `OK`):

- novo catálogo versionado
  `apps/census/data/sector_capacity_catalog_v6.json`, idêntico ao v5 exceto
  em exatamente 2 linhas: `display_name` do grupo `ENF-2B-CARD` muda de
  `Cardioclinica / Enfermaria 2B Cardio` para `Enfermaria 2B Cardio` (e o
  `source_reference` próprio da versão); schema `3.0`, algoritmo
  `occupancy-v5`, capacidade 15 e aliases por código-fonte (`719 →
  Cardioclínica`, `2156 → Enfermaria 2B Cardio`) preservados; catálogos
  históricos (initial/corrected/v3/v4/v5) byte-preserved;

  aliases limpos, sha própria, ativação futura atômica/idempotente, dry-run)
  e 1 teste de caracterização de `/beds` (título exato `Enfermaria 2B Cardio`

  exclusivamente do `display_name` persistido no catálogo.

Comportamento em telas **só muda** com a publicação do catálogo v6 (ação do
operador, seção "Publicação do catálogo v6" abaixo) e, a partir da data
efetiva aprovada, o `/beds` passa a exibir `Enfermaria 2B Cardio` no lugar
correto (junto das demais enfermarias do 2º andar). Até a vigência, e em
todos os dias anteriores ao processamento, o rótulo composto
`Cardioclinica / Enfermaria 2B Cardio` permanece (imutabilidade de versões,

Emenda autorizada durante o slice (registrada no `tasks.md` §7 do change):
critério de formatação "zero drift incremental vs BASE_REF" para os dois
arquivos de teste com drift pré-existente de formatter (precedente Emenda B

## Impacto operacional

- Release de dados (JSON novo) e testes. Nenhuma migration, alteração de
  schema, dependência, variável de ambiente, rota nova, worker novo ou
  mudança de runtime.
- A renomeação exige a publicação explícita do catálogo v6 (management
  command) com data efetiva **estritamente futura** ao hoje local
  (`America/Bahia`). Recomenda-se data = amanhã, executando a publicação
  ainda hoje (antes da meia-noite local): assim o dia seguinte nasce
  integralmente em v6 e nenhum dia local mistura versões.
- Publicação e rollback: o catálogo é imutável — não existe "unpublish".
  Se o dry-run divergir, NÃO publicar (reportar; correção via v7). Se a
  imagem for revertida para a RC29 após a publicação, a v6 permanece no
  banco (inerte até a data efetiva; schema/algoritmo idênticos ao v5,
  apenas `display_name` difere). Cancelar o rename após publicado = versão
  futura v7 com novo change, jamais edição do v6.

## Pré-condições

1. Confirmar que a versão atual é `v0.1.0-rc.29` sem imprimir outras
   variáveis do `.env`.
2. Confirmar PostgreSQL saudável.
3. Registrar a escala atual de `persistent_worker`; o baseline hospitalar é
   de 10 réplicas.
4. Parar temporariamente os produtores de novos ciclos, mantendo os workers
   ativos para drenar a fila.
5. Aguardar `IngestionRun` sem itens `queued` ou `running` e nenhum batch de
   censo aberto.
6. Baixar da release imutável o Compose e este runbook.
7. Criar backup PostgreSQL em formato custom, confirmar arquivo não vazio e
   validar o catálogo com `pg_restore --list`.
8. Ter aprovado a **data efetiva** do v6 (`YYYY-MM-DD` estritamente futura
   ao hoje local `America/Bahia`).

## Pausa e drenagem

No host `eon`, como `root`, em `/srv/apps/prisma`:

```bash

export NEW_VERSION=v0.1.0-rc.30
export COMPOSE_FILE=compose.hospital.yml

systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f "$COMPOSE_FILE" stop census_orchestrator
```


## Download e backup

```bash

  -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"

mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

mkdir -p backups
chmod 700 backups
backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "$backup_path"
test -s "$backup_path"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  pg_restore --list < "$backup_path" >/dev/null
printf 'backup=%s bytes=%s validated=1\n' \
  "$backup_path" "$(stat -c %s "$backup_path")"
```

## Upgrade

```bash
umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${NEW_VERSION}/" .env > .env.new
chmod 600 .env.new
mv .env.new .env
mv compose.hospital.yml.new "$COMPOSE_FILE"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" run --rm web \
  uv run --no-sync python manage.py migrate --noinput

docker compose --env-file .env -f "$COMPOSE_FILE" \
  up -d --remove-orphans --scale persistent_worker=10 \
  db web persistent_worker summary_worker
```

O passo `migrate` deve informar `No migrations to apply`. O orquestrador
permanece parado durante os primeiros smokes.

## Rollback

Como não há migration nova, o rollback é somente de imagem e Compose. Pare
os produtores e drene novamente a fila antes de recriar os workers se o
sistema já tiver retomado o processamento.

```bash
export OLD_VERSION=v0.1.0-rc.29
export COMPOSE_FILE=compose.hospital.yml

systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f "$COMPOSE_FILE" stop census_orchestrator

umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${OLD_VERSION}/" .env \
  > .env.rollback
chmod 600 .env.rollback
mv .env.rollback .env
cp "${COMPOSE_FILE}.${OLD_VERSION}" "$COMPOSE_FILE"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" \
  up -d --remove-orphans --scale persistent_worker=10 \
  db web persistent_worker summary_worker
```

Valide a RC29 antes de reativar o orquestrador e o timer. O backup
PostgreSQL é uma salvaguarda operacional e não deve ser restaurado neste
rollback code-only. Nota específica do v6: se o catálogo já foi publicado,
o rollback de imagem **não** o remove (imutável, sem unpublish) — a v6
permanece inerte até a data efetiva e é compatível com a RC29 (schema e
algoritmo idênticos ao v5; apenas `display_name` difere). Cancelar a
renomeação após publicada exige versão futura v7 com novo change.
