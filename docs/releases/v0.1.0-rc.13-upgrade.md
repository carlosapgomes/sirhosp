# SIRHOSP v0.1.0-rc.13 — Reparo do pipeline persistente de internações (RPAP)

## Status do artefato

Este é o runbook de pré-publicação da candidata `v0.1.0-rc.13`. Ele somente se
torna um asset operacional válido quando anexado, antes da publicação, à
release GitHub imutável da mesma tag e quando a imagem exata existir no GHCR.

O upgrade parte de `v0.1.0-rc.12` (em produção desde 2026-08-27). Esta etapa
repara o pipeline persistente de internações e entrega dois comandos
operacionais novos (`check_ingestion_pipeline_health` e
`recover_current_census_admissions`). Sem migration, sem catálogo e sem
ativação — o `migrate` é executado apenas por idempotência e deve resultar em
`No migrations to apply`. Nenhum comando de recuperação é executado durante o
upgrade: recovery é etapa separada, após canário, conforme
`deploy/README.md` §6.1.3.

## Resumo da release

A RC13 entrega o change OpenSpec `repair-persistent-admissions-pipeline`
(slices RPAP-S1 a RPAP-S6, já arquivado):

- **S1** — o `RealHandleBridge` conserva em memória efêmera o snapshot de
  internações lido no iframe e o entrega ao adapter, sem `set_html()` no
  handle real; o snapshot transitório é limpo em toda nova navegação,
  cleanup, restart, bootstrap, falha e shutdown;
- **S2** — captura vazia em run batch-bound de censo/recuperação falha
  fechado nos dois workers (reason sanitizado `invalid_payload`), sem
  persistir internação nem enfileirar follow-ups; vazio standalone continua
  sendo resultado legítimo;
- **S3** — o censo volta a ser o único produtor de `demographics_only` em
  runs batch-bound; o follow-up demográfico permanece apenas para
  `admissions_only` standalone;
- **S4** — comando `recover_current_census_admissions`: recuperação limitada
  e idempotente a partir do último censo completo, dry-run por padrão,
  `--apply` exige `--limit` (1..100);
- **S5** — comando `check_ingestion_pipeline_health`: diagnóstico agregado
  read-only, fail-closed por exit code, com invariantes batch-bound
  (`empty_success`, `missing_full_sync`, `duplicate_demographics`), idade de
  fila, taxa de falha de full-sync com amostra mínima e frescor opcional;
  saída estritamente sanitizada (sem identificadores, parâmetros, texto
  clínico, URL ou erro bruto);
- **S6** — rejeição do `process_census_snapshot` levanta `CommandError` (não
  `SystemExit`); o orquestrador classifica `processing_failed`, libera o
  advisory lock e mantém o loop vivo.

Também compõem a release, sem impacto de runtime clínico: o commit
`6503ef1` (centraliza o nome da aplicação nos títulos de página) e os
commits de documentação do change anterior (`3614166`, `c454098`,
`6bfd789`, arquivamento e evidence pack da RC12).

A release não altera schema, catálogos, medições, resumos, autenticação,
exact-run, gate de setores, políticas de capacidade nem a história v1–v4.
Não há backfill, ativação ou ensaio de execução. Runs históricos
falsamente bem-sucedidos **não são reabertos**; a recuperação do período do
incidente é operação explícita posterior (dry-run por padrão).

## Verificação da captura de internações por agregados

Este é o critério central do reparo (S1/S2): capturas batch-bound voltam a
produzir internações, e vazio batch-bound novo falha em vez de falsos
sucessos. Verifique somente por contagens, após o primeiro ciclo natural
pós-deploy:

```bash
docker compose --env-file .env -f compose.hospital.yml run --rm web \
  uv run --no-sync python manage.py shell -c \
  'from django.utils import timezone; from datetime import timedelta; from apps.ingestion.models import IngestionRun; since=timezone.now()-timedelta(hours=2); a=IngestionRun.objects.filter(intent="admissions_only", queued_at__gte=since); print({"admissions_enqueued_2h": a.count(), "admissions_succeeded_seen_positive_2h": a.filter(status="succeeded", admissions_seen__gt=0).count(), "admissions_succeeded_seen_zero_2h": a.filter(status="succeeded", admissions_seen=0).count(), "admissions_failed_2h": a.filter(status="failed").count(), "full_sync_enqueued_2h": IngestionRun.objects.filter(intent__in=["full_sync","full_admission_sync"], queued_at__gte=since).count(), "demographics_enqueued_2h": IngestionRun.objects.filter(intent="demographics_only", queued_at__gte=since).count()})'
```

Esperado com pacientes ocupando leitos:

- `admissions_succeeded_seen_positive_2h >= 1` — captura restaurada;
- `admissions_succeeded_seen_zero_2h = 0` — sem falsos sucessos novos
  (batch-bound vazio agora falha; caso ocorra, conta em
  `admissions_failed_2h` com reason `invalid_payload`);
- `full_sync_enqueued_2h >= 1` — follow-ups voltaram a ser criados para
  quem tem internação;
- `demographics_enqueued_2h` consistente com um único produtor por
  batch+patient (censo), sem pico de duplicação.

Não imprima, copie ou registre qualquer linha individual de run, paciente ou
internação; somente estes agregados.

## Fluxo natural pós-deploy

Com orquestrador e dez workers restaurados, o pipeline retoma o ciclo
natural: extração de censo → processamento → movimentações →
`admissions_only` → `full_sync` → evoluções. Reexecute o agregado do
preflight em intervalos regulares nas primeiras horas e confira:

- `baseline_24h.admissions_succeeded_seen_zero` sem crescimento (só
  decai conforme a janela desliza para além do incidente);
- fila drenando (`ingestion_queued`/`ingestion_running` → 0 entre ciclos);
- `full_sync` terminais surgindo e evoluções voltando a ser criadas;
- orquestrador vivo mesmo diante de rejeição de processamento (S6:
  `processing_failed` não derruba o loop; confirme o processo ativo em `ps`).

## Canário e recuperação do incidente (etapa separada, não executar agora)

Após o deploy validado, siga o runbook operacional do
`deploy/README.md` §6.1:

1. **Canário (1–2 semanas):** instale o systemd service+timer genérico do

   **sem provider de alerta ativo** (fora do escopo). Acompanhe
   diariamente `empty_success`, `missing_full_sync`,
   `duplicate_demographics`, `full_sync_failure_reasons` e calibre
   `--settling-minutes`/`--min-full-sync-terminal-sample` se houver falso

2. **Recuperação (após canário estável):** planeje com dry-run
   (`recover_current_census_admissions`, sem mutação), depois aplique em
   lotes pequenos (`--apply --limit 20`), reavaliando o health check entre
   lotes. Runs históricos não são reabertos; a recuperação cria runs novos
   em batch próprio.
3. **Stop conditions e rollback do recovery:** conforme §6.1.3.

## Rollback trivial

A RC13 não muda schema nem reabre dados históricos: o rollback é um
redeploy da RC12 já preservada:

1. pare serviços mutantes na ordem segura (`census_orchestrator web`, drene,
   depois `persistent_worker summary_worker`) — **drene completamente a
   fila antes de reverter**: runs `admissions_only` pendentes processados
   pelo worker da RC12 reproduziriam o falso sucesso vazio do incidente;
2. restaure `compose.hospital.yml.rc12` sobre `compose.hospital.yml`;
3. selecione `SIRHOSP_VERSION=v0.1.0-rc.12` no `.env` sem imprimi-lo;
4. `config --quiet`, `pull` e retome a topologia com dez workers;
5. confirme health, revisão e catálogo v5 identico.

Não reverta migrations nem restaure backup apenas para rollback funcional;
o backup existe para incidentes que exijam restauração coordenada. Runs
criados pela RC13 (batches, admissions, full-syncs novos) são linhas com
schema inalterado e permanecem válidos sob a RC12.
