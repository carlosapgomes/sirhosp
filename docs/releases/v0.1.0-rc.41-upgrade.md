# Runbook de upgrade — v0.1.0-rc.41

Upgrade hospitalar da `v0.1.0-rc.40` para a `v0.1.0-rc.41`.

## Escopo

- `e42abfa` — DD-S1: matching de óbito date-only no planner
  (`reconcile_admission_history` passa a planejar a coorte `deaths` com
  evidência de apenas data; `deaths:date_only` deixa de existir como
  reason de revisão; datetime completo inalterado).
- `ba37b89` — DD-S2: apply de óbito date-only fecha a internação em
  D 00:00 `America/Bahia` (portadora da data) com marcador
  `death_exit={"precision": "date", "local_date": D}` no evento;
  `obito_em` nunca é sintetizado; rollback restaura internação e
  evidência com o status pré-apply exato; superfícies (portal e admin)
  exibem apenas a data para fechamentos date-only.
- Change OpenSpec: `reconcile-date-only-deaths` (specs
  `admission-exit-reconciliation` e `admission-reconciliation-backfill`
  sincronizadas no archive; design D2 aceito pelo operador 2026-10-25).

## Impacto operacional

- **Sem migrations** (o passo `migrate` é no-op nesta release).
- Sem novas dependências; `compose.hospital.yml` (`cd0e444c…`), Dockerfile
  e units idênticos aos da rc.34–rc.40.
- Mudança de comportamento clínico: óbitos com apenas data passam a poder
  reconciliar em precisão de data (unicidade obrigatória; ambíguos
  permanecem fail-closed em revisão manual com reason explícito).
- Óbitos continuam excluídos dos indicadores de altas hospitalares.
- **Esta release existe para a ativação da regularização dos óbitos
  históricos** (seção própria abaixo): ~777 registros `date_only` deixam
  de ser um bucket mudo e passam a ter desfecho explícito (reconciliado
  ou reason de revisão).

## Pré-condições

1. Confirmar a versão atual (`v0.1.0-rc.40`) sem imprimir outras variáveis
   do `.env`.
2. Confirmar PostgreSQL saudável.
3. Registrar a escala atual de `persistent_worker`; o baseline hospitalar é
   de 10 réplicas.
4. Parar temporariamente os produtores de novos ciclos (`census_orchestrator`
   e `sirhosp-stale-reconciliation.timer`), mantendo os workers ativos para
   drenar a fila.
5. Aguardar `IngestionRun` sem itens `queued` ou `running` e nenhum batch de
   censo aberto (mesma checagem de drenagem da seção 5c do `deploy/README.md`).
6. Baixar da release imutável o Compose, os units e este runbook.
7. Criar backup PostgreSQL em formato custom, confirmar arquivo não vazio e
   validar o catálogo com `pg_restore --list`.
8. Confirmar que os três timers de fallback (`sirhosp-discharges.timer`,
   `sirhosp-historical-recovery.timer` e `sirhosp-daily-statistics.timer`)
   estão `disabled` e `inactive`.
9. Combinar com o operador a janela da ativação de óbitos (seção própria):
   o dry-run pós-deploy define os números; nenhum `--apply` sem leitura e
   aprovação explícita dos contadores.

## Pausa e drenagem

No host hospitalar, como `root`, em `/srv/apps/prisma`:

```bash
systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f compose.hospital.yml stop census_orchestrator
```

Confirme a drenagem antes de recriar os workers:

```bash
drain_state="$(
  docker compose --env-file .env -f compose.hospital.yml exec -T web \
    uv run --no-sync python -c \
    'import os,django; os.environ.setdefault("DJANGO_SETTINGS_MODULE","config.settings"); django.setup(); from apps.ingestion.models import IngestionRun,CensusExecutionBatch; print(IngestionRun.objects.filter(status__in=("queued","running")).count(), CensusExecutionBatch.objects.filter(status="running").count())'
)"
printf 'drain_state=%s\n' "$drain_state"
test "$drain_state" = "0 0"
```

Se ainda houver itens ativos, aguarde com os 10 workers em execução. Não
prossiga com a drenagem pendente.

## Download e backup

```bash
set -euo pipefail
export OLD_VERSION=v0.1.0-rc.40
export NEW_VERSION=v0.1.0-rc.41
export COMPOSE_FILE=compose.hospital.yml
cd /srv/apps/prisma
mkdir -p backups deploy/systemd
chmod 700 backups
curl -fL --retry 3 -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"
curl -fL --retry 3 -o "${COMPOSE_FILE}.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${COMPOSE_FILE}"
curl -fL --retry 3 -o deploy/exit-reconciliation-scheduler.sh \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/exit-reconciliation-scheduler.sh"
curl -fL --retry 3 -o deploy/daily-statistics-activation-preflight.sh \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/daily-statistics-activation-preflight.sh"
chmod +x deploy/exit-reconciliation-scheduler.sh deploy/daily-statistics-activation-preflight.sh
for unit in sirhosp-discharges.service sirhosp-discharges.timer \
  sirhosp-historical-recovery.service sirhosp-historical-recovery.timer \
  sirhosp-stale-reconciliation.service sirhosp-stale-reconciliation.timer \
  sirhosp-daily-statistics.service sirhosp-daily-statistics.timer; do
  curl -fL --retry 3 -o "deploy/systemd/${unit}" \
    "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${unit}"
done
sha256sum "${COMPOSE_FILE}.new"
cp -p "$COMPOSE_FILE" "${COMPOSE_FILE}.${OLD_VERSION}"
mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f $COMPOSE_FILE exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > "${backup_path}"
test -s "${backup_path}"
docker compose --env-file .env -f $COMPOSE_FILE exec -T db pg_restore --list < "${backup_path}" >/dev/null
echo "backup=${backup_path}"
```

O hash do Compose deve ser `cd0e444c…` (idêntico à rc.34–rc.40).

## Upgrade

```bash
umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${NEW_VERSION}/" .env > .env.new
grep -n "^SIRHOSP_VERSION=${NEW_VERSION}$" .env.new
chmod 600 .env.new && mv .env.new .env
mv ${COMPOSE_FILE}.new $COMPOSE_FILE
docker compose --env-file .env -f $COMPOSE_FILE config --quiet

docker compose --env-file .env -f $COMPOSE_FILE pull
docker compose --env-file .env -f $COMPOSE_FILE run --rm web \
  uv run --no-sync python manage.py migrate --noinput
docker compose --env-file .env -f $COMPOSE_FILE up -d --remove-orphans \
  --scale persistent_worker=10 db web persistent_worker summary_worker

install -m 0644 deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
systemctl daemon-reload
```

Esta release **não tem migrations**: o `migrate` deve reportar
`No migrations to apply.` (ou apenas os já aplicados). Qualquer migração
inesperada aqui é critério de parada.

**Dry-run da nova capacidade (leitura, sem mutação):**

```bash

  uv run --no-sync python manage.py reconcile_admission_history --limit 5000
```

Esperado: `cohort=deaths eligible=N bounded=N` com N > 0 e **ausência** do
reason `deaths:date_only`. Guarde a saída: os contadores
(`eligible`, `deaths:ambiguous`, `deaths:patient_not_found`,
`deaths:admission_not_found`) definem o plano de ativação abaixo.

## Ativação da regularização de óbitos (operação delimitada)

Pré-requisitos: drenagem concluída, backup válido (o mesmo caminho serve de
`--backup-ref`), dry-run lido e aprovado pelo operador.

1. **Canário** (cap 50 quando é o primeiro batch do dia; a existência de
   batches anteriores eleva o cap a 100 — o comando impõe o limite):

   ```bash
   docker compose --env-file .env -f $COMPOSE_FILE exec -T web \
     uv run --no-sync python manage.py reconcile_admission_history \
     --apply --limit 50 --label deaths-date-only-activation-canary \
     --backup-ref "${backup_path}"
   ```

2. **Verificação do canário** (auditoria + zero erro):

   ```bash
   docker compose --env-file .env -f $COMPOSE_FILE exec -T web \
     uv run --no-sync python -c \
     'import os,django; os.environ.setdefault("DJANGO_SETTINGS_MODULE","config.settings"); django.setup(); from apps.patients.models import ReconciliationEvent; from django.db.models import Count; qs=ReconciliationEvent.objects.filter(details_json__death_exit__precision="date"); print("eventos_date_only:", qs.count()); print(qs.values("exit_type").annotate(n=Count("id")))'
   docker compose --env-file .env -f $COMPOSE_FILE logs --since 10m web | grep -iE 'error|traceback' || true
   ```

3. **Lotes ≤100** até `plan_items=0` no dry-run, cada lote com `--label`
   sequencial (`deaths-date-only-activation-batch2`, `batch3`, …) e o mesmo
   `--backup-ref` do backup pré-operação.

4. **Rollback pontual** (se um lote precisar ser revertido; valida
   pós-estado e restaura internação + evidência com status pré-apply
   exato):

   ```bash
   docker compose --env-file .env -f $COMPOSE_FILE exec -T web \
     uv run --no-sync python manage.py rollback_admission_reconciliation \
     --batch <batch_uuid-do-lote>
   ```

5. **Conferência final**: dry-run com todas as coortes `eligible=0`;
   episódios fechados por morte com marcador `precision=date`; relatório de
   revisão manual com os reasons explícitos (`deaths:ambiguous`,
   `deaths:patient_not_found`, `deaths:admission_not_found`) — esses
   permanecem fail-closed por design; indicadores de altas inalterados
   (óbitos continuam excluídos).

## Rollback

- **Imagem**: recriar os containers com `SIRHOSP_VERSION=v0.1.0-rc.40`.
  Sem migrations nesta release, não há schema a reverter; não restaurar o
  banco apenas para voltar a versão.
- **Ativação de óbitos**: os lotes aplicados são reversíveis por batch
  (comando da seção anterior), sem restaurar banco. Batches antigos
  permanecem válidos.
- Nunca desfazer migrations nem restaurar o banco como parte do rollback
  desta release.
