# Runbook de Upgrade — v0.1.0-rc.32 (2026-09-27)

## Escopo

Esta release entrega a **finalização estatística adaptativa** do change
`orchestrate-adaptive-statistics-finalization` (ADR-0012, com a ADR-0010 e a
ADR-0011):

- o `census_orchestrator` passa a finalizar a data D-1 dentro do próprio loop,
  depois da tentativa D-1 e na primeira iteração em que a fila esteja drenada e
  nenhum batch de censo esteja aberto, antes da recuperação intradiária e do
  próximo ciclo censitário;
- o Compose hospitalar passa a entregar explicitamente
  `STATISTICS_ACTIVATION_DATE` (default **vazio fail-closed**) e
  `STATISTICS_FINALIZATION_LOOKBACK_DAYS` (default 7) ao `census_orchestrator`;
- a revisão pode ser publicada com o aviso técnico enumerado
  `d1_recovery_incomplete` (falha D-1 observada) ou `d1_recovery_not_confirmed`
  (processo reiniciado que não pôde comprovar o resultado anterior);
- o preflight `daily-statistics-activation-preflight.sh` passa a validar o
  runtime adaptativo: comparação byte a byte do Compose e dos units instalados,
  os três timers de fallback `disabled`/`inactive`, evidência natural hourly/D-1
  nos logs do container e bootstrap da data corrente apenas antes das 20:00
  `America/Bahia`;
- os services one-shot `sirhosp-daily-statistics`, `sirhosp-discharges` e
  `sirhosp-historical-recovery` permanecem como **fallback manual inerte**, com
  os três timers desabilitados e inativos no caminho primário.

Base do upgrade: **v0.1.0-rc.31** (`75f88c9`).

O intervalo `v0.1.0-rc.31..HEAD` altera `apps/census/orchestration.py`, o
comando `materialize_daily_statistics`, `compose.hospital.yml`, o preflight, os
contratos estáticos dos units, `deploy/README.md` e `.env.example`. **Nenhuma
migration** é adicionada ou removida. **Nenhuma credencial nova** entra no
`.env`: as duas variáveis estatísticas são opcionais e têm default seguro.
SHA-256 do Compose desta release:
`cd0e444c9316a8b267823f31cf1d4a1fee40e7bf2b96b9aa27da10002f4f9dc1`.

Validação anterior à tag:

- `./scripts/test-in-container.sh unit`;
- `./scripts/test-in-container.sh integration`;
- `./scripts/test-in-container.sh check`;
- `./scripts/test-in-container.sh lint`;
- `./scripts/test-in-container.sh typecheck`;
- `./scripts/markdown-lint.sh`;
- `openspec validate orchestrate-adaptive-statistics-finalization --strict`.

## Limite operacional desta release

A publicação e o upgrade da imagem **não ativam** a finalização estatística.
Instalação dos assets, configuração da fronteira, preflight, aprovação humana
e ativação são checkpoints separados, descritos na seção 5c de `deploy/README.md`.

Durante o upgrade:

- não configure `STATISTICS_ACTIVATION_DATE` na etapa de deploy dormente;
- não instale nem ligue `sirhosp-daily-statistics.timer`; mantenha os três
  timers de fallback `disabled`/`inactive`;
- não execute backfill, extração ou materialização manual;
- não simule marcadores de log nem cadências upstream;
- não trate a disponibilidade dos assets como autorização para ativação.

O deploy desta release é **dormente**: a imagem, o Compose e os assets são
instalados, `web` e workers são atualizados e o `census_orchestrator` continua
executando a versão anterior até a recriação isolada da ativação. Assim as
evidências naturais hourly/D-1 recentes permanecem legíveis pelos logs do
container antes da recriação.

## Impacto operacional

- Nenhuma migration: o schema é idêntico ao da RC31.
- Nenhuma variável obrigatória nova e nenhuma credencial nova.
- O orquestrador ganha o passo curto de finalização estatística: sem daemon,
  fila, Celery, Redis ou tabela nova.
- Os units de fallback e suas descrições mudam apenas como contrato
  documental; nenhum deles passa a ser habilitado automaticamente.
- Não existe backfill anterior à fronteira e nenhum dia anterior à ativação é
  reconstruído.
- O rollback de imagem não exige desfazer migrations: as revisões já
  materializadas permanecem auditáveis.

## Pré-condições

1. Confirmar que a versão atual é `v0.1.0-rc.31` sem imprimir outras variáveis
   do `.env`.
2. Confirmar PostgreSQL saudável.
3. Registrar a escala atual de `persistent_worker`; o baseline hospitalar é de
   10 réplicas.
4. **Não parar o `census_orchestrator`**: ele deve continuar executando para que
   o preflight leia a evidência natural hourly/D-1 coletada antes da recriação.
5. Aguardar `IngestionRun` sem itens `queued` ou `running` e nenhum batch de
   censo aberto (mesma checagem de drenagem da seção 5c do `deploy/README.md`).
6. Baixar da release imutável o Compose, os units e este runbook.
7. Criar backup PostgreSQL em formato custom, confirmar arquivo não vazio e
   validar seu catálogo com `pg_restore --list`.
8. Confirmar que os três timers de fallback (`sirhosp-discharges.timer`,
   `sirhosp-historical-recovery.timer` e `sirhosp-daily-statistics.timer`)
   estão `disabled` e `inactive` com `systemctl is-enabled` / `is-active`.

## Download, backup e deploy dormente

```bash
set -euo pipefail
export OLD_VERSION=v0.1.0-rc.31
export NEW_VERSION=v0.1.0-rc.32
export COMPOSE_FILE=compose.hospital.yml
cd /srv/apps/prisma

mkdir -p backups deploy/systemd
chmod 700 backups

curl -fL --retry 3 -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"
curl -fL --retry 3 -o "${COMPOSE_FILE}.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${COMPOSE_FILE}"

# Scheduler, preflight e TODOS os units da MESMA tag: o preflight compara byte a
# byte o que está instalado e reprova cópia local divergente.
curl -fL --retry 3 -o deploy/exit-reconciliation-scheduler.sh \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/exit-reconciliation-scheduler.sh"
curl -fL --retry 3 -o deploy/daily-statistics-activation-preflight.sh \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/daily-statistics-activation-preflight.sh"
chmod +x deploy/exit-reconciliation-scheduler.sh deploy/daily-statistics-activation-preflight.sh
for unit in \
  sirhosp-discharges.service sirhosp-discharges.timer \
  sirhosp-historical-recovery.service sirhosp-historical-recovery.timer \
  sirhosp-stale-reconciliation.service sirhosp-stale-reconciliation.timer \
  sirhosp-daily-statistics.service sirhosp-daily-statistics.timer; do
  curl -fL --retry 3 -o "deploy/systemd/${unit}" \
    "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${unit}"
done
cp -p "$COMPOSE_FILE" "${COMPOSE_FILE}.${OLD_VERSION}"
mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "${backup_path}"
test -s "${backup_path}"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  pg_restore --list < "${backup_path}" >/dev/null
printf 'backup=%s bytes=%s validated=1\n' "${backup_path}" "$(stat -c %s "${backup_path}")"
```

## Fronteira e preflight fail-closed

Declare a fronteira no `.env` do hospital: uma data **futura** em
`America/Bahia` ou, excepcionalmente no primeiro dia, a data local corrente
somente **antes das 20:00** locais (data passada nunca é aceita). O preflight
`daily-statistics-activation-preflight.sh` é **somente leitura** e
**fail-closed**: valida a tag publicada e imutável, a procedência byte a byte
dos assets instalados (Compose, scheduler, preflight e units), a versão da
imagem, a fronteira, o estado `disabled`/`inactive` dos três timers de fallback,
a existência do serviço `census_orchestrator` e a evidência agregada natural
hourly (2 horas) e D-1 (30 horas) nos logs do container.

A consulta ao runtime usa apenas operações Docker de leitura (`compose ps` e
`compose logs --since <janela> --no-color`) e exige do operador o **privilégio de
leitura do socket do Docker**; nenhum estado do host é alterado.

```bash
set -euo pipefail
cd /srv/apps/prisma
export NEW_VERSION=v0.1.0-rc.32

activation_date=2026-11-01   # data local America/Bahia: futura, ou a corrente antes das 20:00
test -n "${activation_date}"
sed -i "s/^STATISTICS_ACTIVATION_DATE=.*/STATISTICS_ACTIVATION_DATE=${activation_date}/" .env
grep -n '^STATISTICS_ACTIVATION_DATE=[0-9]' .env

./deploy/daily-statistics-activation-preflight.sh "${NEW_VERSION}" \
  | tee "/tmp/sirhosp-preflight-${NEW_VERSION}.txt" \
  || { echo 'preflight reprovado (status != 0) — ativação bloqueada' >&2; exit 1; }

echo "preflight=PASS new_version=${NEW_VERSION}"
```

`[preflight] result=PASS` é pré-condição, não autorização: se o preflight
reprovar, corrija a causa e colete uma saída nova. A evidência expira com as
janelas de 2 horas (hourly) e 30 horas (D-1). Nenhum extrator é disparado para
produzir evidência: aguarde a próxima execução natural do orquestrador.

## Aceite humano e ativação isolada

Registre no ticket da organização a tag exata, o `[preflight] result=PASS` e as
contagens agregadas — nunca anexe log bruto do container, credencial, workbook ou
dados nominais. Só depois do aceite humano explícito e com a
evidência ainda fresca, recrie **somente** o `census_orchestrator`.

## Observação

A primeira finalização natural ocorre depois da tentativa D-1 e da primeira
drenagem segura. Observe somente evidência agregada — datas, revisões, status,
contagens e marcadores:

```bash
set -euo pipefail
cd /srv/apps/prisma
export COMPOSE_FILE=compose.hospital.yml

docker compose --env-file .env -f "$COMPOSE_FILE" logs --since 30h --no-color census_orchestrator \
  | grep -E 'mode=(d1-recovery|hourly-discharges) result=success source=adaptive-orchestrator|Daily statistics finalization (finished|failed)|date=|status=|revision=|created=|quality='
```

- `date=` e `revision=` identificam a data local e a revisão publicada;
- `status=ready` e `created=true|false` mostram publicação e idempotência;
- `quality=` traz o aviso técnico persistido (`d1_recovery_incomplete` ou
  `d1_recovery_not_confirmed`) sem substituir a evidência das cadências;
- `Daily statistics finalization finished: local date <D-1>, duration <s>`
  confirma a passagem do passo adaptativo e `failed` registra apenas a classe
  técnica.

Nunca copie para o terminal, ticket ou anexo nomes, prontuários, leitos, texto
clínico ou log bruto: a observação usa **identidade** nenhuma, apenas contagens
agregadas.

Recuperação adaptativa pós-05:00 e checkpoint das 07:30:

- um processo reiniciado **depois das 05:00** `America/Bahia` que não encontre
  revisão `ready` para a data D-1 faz **uma única** tentativa de recuperação na
  primeira drenagem segura e publica a revisão com `d1_recovery_not_confirmed`;
  ele não reabre o D-1 fora da janela, não varre histórico e não depende de ação
  do operador;
- às **07:30**, se ainda não existir revisão `ready` para a data esperada, o
  checkpoint **alerta** e exige **decisão humana**: nenhum retry automático e
  nenhuma extração é disparada por calendário;
- o fallback manual só remove `d1_recovery_incomplete` ou
  `d1_recovery_not_confirmed` **depois de sucesso D-1 comprovado** para a mesma
  data, com um rerun explícito de `materialize_daily_statistics --date` sem
  aviso. Sem essa evidência, preserve o aviso e investigue: o fallback manual
  **nunca usa `--finalize` para limpá-lo**.

## Rollback

O rollback remove a fronteira estatística e retorna imagem e Compose à RC31.
Ele **não** apaga revisões materializadas, **não** altera fontes clínicas e
**não** reverte ou restaura o banco: **Nenhuma migration** é desfeita no
rollback rotineiro. Nenhum timer de fallback é habilitado — os três permanecem
`disabled`/`inactive`.

```bash
set -euo pipefail
cd /srv/apps/prisma
export OLD_VERSION=v0.1.0-rc.31
export COMPOSE_FILE=compose.hospital.yml

umask 077
cp -p .env ".env.bak-$(date -u +%Y%m%dT%H%M%SZ)"
sed -i 's/^STATISTICS_ACTIVATION_DATE=.*/STATISTICS_ACTIVATION_DATE=/' .env
grep -n '^STATISTICS_ACTIVATION_DATE=$' .env
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${OLD_VERSION}/" .env > .env.rollback
chmod 600 .env.rollback
mv .env.rollback .env
cp "${COMPOSE_FILE}.${OLD_VERSION}" "${COMPOSE_FILE}"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" up -d --no-deps --force-recreate census_orchestrator
docker compose --env-file .env -f "$COMPOSE_FILE" ps census_orchestrator
```

Depois do rollback:

- confirme `health=ok` com o mesmo comando da seção de validação;
- confirme as revisões materializadas por contagem agregada, sem imprimir
  conteúdo do relatório;
- confirme o timer de fallback `disabled`/`inactive` (`systemctl is-enabled`,
  `systemctl is-active`);
- se o objetivo for devolver também os assets à RC31, reinstale os units daquela
  tag com a mesma sequência download/instalação da etapa dormente, mantendo os
  três timers `disabled`/`inactive`;
- mantenha a cadência intradiária de altas do orquestrador em execução: o
  rollback interrompe apenas a finalização estatística;
- a restauração do backup PostgreSQL é uma medida de contingência: só a execute
  por decisão específica, com investigação, se houver incompatibilidade não
  esperada.
