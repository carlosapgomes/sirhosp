# SIRHOSP v0.1.0-rc.15 — Correção do esgotamento de tentativas de full-sync (FX)

## Status do artefato

Este é o runbook de pré-publicação da candidata `v0.1.0-rc.15`. Ele somente se
torna um asset operacional válido quando anexado, antes da publicação, à
release GitHub imutável da mesma tag e quando a imagem exata existir no GHCR.

O upgrade parte de `v0.1.0-rc.14` (em produção desde 2026-08-29). Esta release
entrega o change OpenSpec `fix-fullsync-failure-exhaustion` (slices FX-S1 a
FX-S4, verificados por LLM terceiro e arquivado como
`2026-08-29-fix-fullsync-failure-exhaustion`): a correção das causas
comprovadas na ADR-0008 — fail-fast determinístico e orçamento por volume —
além da suíte de caracterização das validações de payload. Sem migration, sem
catálogo, sem dependência nova e **sem comando novo de produção**: o `migrate`
é executado apenas por idempotência e deve resultar em `No migrations to
apply`.

Nenhum `--apply`, recovery, reprocessamento ou reenfileiramento é executado
durante o upgrade. Runs históricos não são mutados nem reabertos; a correção
atua apenas no comportamento dos workers para tentativas futuras.

O critério central desta release é o rollout da correção com o **baseline
pré-rollout** e a **observação §6.3.2** do `deploy/README.md` (comandos
existentes apenas): health check (`full_sync_failure_reasons`,
`failure_percent`), caracterização (`attempts_median`/`attempts_max`) e stage
metrics de `evolution_extraction`.

Decisão do operador registrada: o worker clássico
(`process_ingestion_runs`) **não recebe o orçamento por volume** — permanece
fora da topologia de produção e sua remoção futura é a direção acordada
(motivo: custo de processamento da sessão não-persistente, razão da migração
para o worker persistente). O fail-fast (FX-S1) já cobre os dois workers por
ser política de requeue compartilhada.

## Resumo da release

A RC15 entrega o change `fix-fullsync-failure-exhaustion` (4 slices,
verificação independente COMPLETE):

- **FX-S1** — política pura `should_retry_failure_reason`
  (`apps/ingestion/run_lifecycle.py`): `invalid_payload` é determinístico e
  termina o run `failed` na **primeira** tentativa (sem requeue, com
  `FinalRunFailure` e fechamento de batch); `timeout` e demais reasons
  mantêm retry +60s. Aplicada aos dois workers
  (`_mark_run_failed`); log fail-fast agregado e sanitizado. A coorte
  fail-only (ADR-0008: 23 pacientes, 453 runs, mediana 15, máx 112
  tentativas) deixa de queimar execuções;
- **FX-S2** — função pura `evolution_window_budget_seconds`
  (`apps/ingestion/extractors/persistent_evolution_pdf.py`): orçamento por
  janela de gap `120s + 2s/dia` de span, teto `600s`, aplicado no laço de
  evoluções do worker persistente em vez do `timeout=120` fixo. Semântica
  bounded (deadline único D14) preservada; volume acima do teto continua
  falhando `timeout`;
- **FX-S3** — suíte de caracterização
  (`tests/unit/test_evolution_payload_validation_characterization.py`)
  pinando as 6 validações de payload contra o código real, com prova de
  sensibilidade por mutação (2 mutações → 4 falhas → reverts verdes);
  veredito **sem lacuna de parsing** registrado (o resgate por viewer frame
  para `data` vazio já existe e está coberto);
- **FX-S4** — regressão do laboratório CFC (9/9 vereditos idênticos
  pré/pós-correção), nota operacional `deploy/README.md` §6.3 (como observar
  pós-rollout com comandos existentes) e verificação final do change.

Também compõem a release, sem impacto de runtime: o evidence pack da RC14
(`11be909`), o arquivamento do CFC (`7d0cae6`) e os artefatos do change FX
(`fd93aee`, `6cd85e4` — OpenSpec, gitignored exceto specs/archive).

Testes: unit 2991 → **3019** (+42: 14 FX-S1, 18 FX-S2, 10 FX-S3);
integration 391 constante; todos os gates verdes em todos os slices.

A release não altera schema, catálogos, medições, resumos, autenticação,
orquestrador ou a topologia de produção.

## Health check pós-deploy e observação §6.3.2

Execute a leitura informativa com janela 2h e, na sequência, a 24h (registrar
ambas):

```bash
docker compose --env-file .env -f compose.hospital.yml exec -T web \
  uv run --no-sync python manage.py check_ingestion_pipeline_health \
  --window-hours 2
docker compose --env-file .env -f compose.hospital.yml exec -T web \
  uv run --no-sync python manage.py check_ingestion_pipeline_health
```

Esperado: `empty_success=0` e `duplicate_demographics=0` em ambas. A taxa de
falha pode subir ou cair transitória na janela curta (runs longos ganham
orçamento; determinísticos terminam rápido) — o sinal relevante é a tendência
da `failure_percent` na janela de 24h nas horas seguintes.

**Observação da correção (§6.3.2, ao longo das horas/dias seguintes):**

1. health check: `full_sync_failure_reasons` — tentativas de
   `invalid_payload` caem (fail-fast na 1ª) e `failure_percent` cai com a
   redução da queima semanal;
2. caracterização (§6.2.1): `attempts_median`/`attempts_max` da coorte caem
   à medida que runs novos entram na janela (terminais com
   `FinalRunFailure.attempts_exhausted=1` nos fail-fast); runs
   recuperados por orçamento deixam de compor a coorte;
3. stage metrics: p90 de `evolution_extraction` converge para valores abaixo
   do teto 600s conforme janelas longas deixam de estourar o orçamento fixo.

```bash
docker compose --env-file .env -f compose.hospital.yml exec -T web \
  uv run --no-sync python manage.py characterize_fullsync_failures \
  --window-hours 168 --min-attempts 3
```

## Rollback trivial

A RC15 não muda schema nem escreve dados clínicos novos: o rollback é um
redeploy da RC14 já preservada:

1. pare serviços mutantes na ordem segura (`census_orchestrator web`, drene,
   depois `persistent_worker summary_worker`), com drenagem completa da
   fila antes de reverter;
2. restaure `compose.hospital.yml.rc14` sobre `compose.hospital.yml`;
3. selecione `SIRHOSP_VERSION=v0.1.0-rc.14` no `.env` sem imprimi-lo;
4. `config --quiet`, `pull` e retome a topologia com dez workers;
5. confirme health, revisão e catálogo v5 idêntico.

Nota: o rollback restaura o retry cego e o orçamento fixo (comportamento
pré-correção); nenhum dado é afetado. Não reverta migrations nem restaure
backup para rollback funcional; o backup existe para incidentes que exijam
restauração coordenada. Runs terminados pela RC15 (fail-fast com 1 tentativa)
permanecem válidos sob a RC14 — apenas tentativas futuras voltam ao
comportamento antigo.
