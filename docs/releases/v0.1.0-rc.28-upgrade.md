# Runbook de Upgrade — v0.1.0-rc.28 (2026-09-09)

## Escopo

Conclui o change `show-captured-patient-exits-on-dashboard` iniciado na RC27:

- o card diário de altas passa a contar saídas efetivas por
  `DischargeRecord.saida_em`, inclusive evidências pendentes, ambíguas ou em
  conflito;
- `alta_em` sem `saida_em` não entra no card gerencial de saída;
- o dashboard deixa de apresentar sumários como um segundo card primário de
  alta;
- a listagem acessada pelo gráfico consulta diretamente `DischargeRecord` por
  `saida_em` na data local de `America/Bahia`;
- `/reconciliacao/`, já protegido por `review_reconciliation_cases`, recebe um
  comparativo agregado entre saídas capturadas, saídas canônicas reconciliadas e
  sumários médicos;
- o comparativo usa eixo consecutivo, dias zerados e payload sem identidade;
- períodos solicitados por `?dias` ficam limitados a 365 dias, com fallback para
  90 quando inválidos;
- a ADR-0009 passa a distinguir a métrica gerencial de evidência da métrica
  canônica de domínio.

Base do upgrade: **v0.1.0-rc.27** (`961572b`).

Validação do release:

- 3.591 testes unitários;
- 695 testes de integração;
- Django check, Ruff e mypy;
- quality gate oficial em container;
- OpenSpec estrito e Markdown lint.

## Impacto operacional

- Release somente de código, templates, testes e documentação.
- Nenhuma migration, alteração de schema ou nova variável de ambiente.
- Nenhuma alteração em modelos, workers, timers, comandos de backfill ou regras
  de reconciliação.
- Nenhum backfill ou reprocessamento clínico é executado pelo deploy.
- `DailyDischargeCount` preserva sua semântica canônica definida pela ADR-0009.
- A página protegida de reconciliação executa três agregações adicionais,
  limitadas a no máximo 365 dias. Monitorar latência e planos de consulta se o
  volume crescer.

## Pré-condições

1. Confirmar que a versão atual é `v0.1.0-rc.27` sem imprimir outras variáveis
   do `.env`.
2. Confirmar PostgreSQL saudável.
3. Registrar a escala atual de `persistent_worker`; o baseline hospitalar é de
   10 réplicas.
4. Parar temporariamente os produtores de novos ciclos, mantendo os workers
   ativos para drenar a fila.
5. Aguardar `IngestionRun` sem itens `queued` ou `running` e nenhum batch de
   censo aberto.
6. Baixar da release imutável o Compose e este runbook.
7. Criar backup PostgreSQL em formato custom, confirmar arquivo não vazio e
   validar o catálogo com `pg_restore --list`.

## Pausa e drenagem

No host `eon`, como `root`, em `/srv/apps/prisma`:

```bash
export OLD_VERSION=v0.1.0-rc.27
export NEW_VERSION=v0.1.0-rc.28
export COMPOSE_FILE=compose.hospital.yml

systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f "$COMPOSE_FILE" stop census_orchestrator
```

Confirme a drenagem antes de recriar os workers:

```bash
drain_state="$(
  docker compose --env-file .env -f "$COMPOSE_FILE" exec -T web \
    uv run --no-sync python -c \
    'import os,django; os.environ.setdefault("DJANGO_SETTINGS_MODULE","config.settings"); django.setup(); from apps.ingestion.models import IngestionRun,CensusExecutionBatch; print(IngestionRun.objects.filter(status__in=("queued","running")).count(), CensusExecutionBatch.objects.filter(status="running").count())'
)"
printf 'drain_state=%s\n' "$drain_state"
test "$drain_state" = "0 0"
```

Se ainda houver itens ativos, aguarde com os 10 workers em execução. Não reinicie
containers durante a drenagem.

## Download e backup

```bash
curl -fL --retry 3 \
  -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"
curl -fL --retry 3 \
  -o compose.hospital.yml.new \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/compose.hospital.yml"

cp -p "$COMPOSE_FILE" "${COMPOSE_FILE}.${OLD_VERSION}"
mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

mkdir -p backups
chmod 700 backups
backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "$backup_path"
test -s "$backup_path"
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T db \
  pg_restore --list < "$backup_path" >/dev/null
printf 'backup=%s bytes=%s validated=1\n' \
  "$backup_path" "$(stat -c %s "$backup_path")"
```

## Upgrade

```bash
umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${NEW_VERSION}/" .env > .env.new
chmod 600 .env.new
mv .env.new .env
mv compose.hospital.yml.new "$COMPOSE_FILE"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" run --rm web \
  uv run --no-sync python manage.py migrate --noinput

docker compose --env-file .env -f "$COMPOSE_FILE" \
  up -d --remove-orphans --scale persistent_worker=10 \
  db web persistent_worker summary_worker
```

O orquestrador permanece parado durante os primeiros smokes.

## Validação antes de retomar produtores

```bash
docker compose --env-file .env -f "$COMPOSE_FILE" ps
docker compose --env-file .env -f "$COMPOSE_FILE" exec -T web \
  uv run --no-sync python manage.py check

health_host="$(
  grep -E '^DJANGO_ALLOWED_HOSTS=' .env | cut -d= -f2- | cut -d, -f1
)"
host_port="$(grep -E '^DJANGO_PORT=' .env | cut -d= -f2-)"
test -n "$health_host"
test -n "$host_port"

curl -fsS -H "Host: $health_host" \
  "http://127.0.0.1:${host_port}/health/"
for path in painel/ painel/altas/ altas/ reconciliacao/; do
  code="$(
    curl -sS -o /dev/null -w '%{http_code}' -H "Host: $health_host" \
      "http://127.0.0.1:${host_port}/${path}"
  )"
  printf '%s http=%s\n' "$path" "$code"
  test "$code" = "302"
done
```

Critérios de aceite antes da retomada:

- web saudável e `/health/` responde com sucesso;
- rotas autenticadas redirecionam usuário anônimo para login;
- 10 réplicas de `persistent_worker` estão ativas;
- web, workers e worker de sumários usam a tag exata `v0.1.0-rc.28`;
- migrations estão aplicadas e os containers não apresentam crash loop.

## Rollback

Como não há migration nova, o rollback é somente de imagem e Compose. Pare os
produtores e drene novamente a fila antes de recriar os workers se o sistema já
tiver retomado o processamento.

```bash
export OLD_VERSION=v0.1.0-rc.27
export COMPOSE_FILE=compose.hospital.yml

systemctl stop sirhosp-stale-reconciliation.timer
docker compose --env-file .env -f "$COMPOSE_FILE" stop census_orchestrator

umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${OLD_VERSION}/" .env \
  > .env.rollback
chmod 600 .env.rollback
mv .env.rollback .env
cp "${COMPOSE_FILE}.${OLD_VERSION}" "$COMPOSE_FILE"

docker compose --env-file .env -f "$COMPOSE_FILE" config --quiet
docker compose --env-file .env -f "$COMPOSE_FILE" pull
docker compose --env-file .env -f "$COMPOSE_FILE" \
  up -d --remove-orphans --scale persistent_worker=10 \
  db web persistent_worker summary_worker
```

Valide a RC27 antes de reativar o orquestrador e o timer. O backup PostgreSQL é
uma salvaguarda operacional e não deve ser restaurado neste rollback code-only.
Pare e investigue antes de qualquer restauração de banco.
