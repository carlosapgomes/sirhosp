# SIRHOSP v0.1.0-rc.9 — Duas realidades de ocupação

## Status do artefato

Este é o runbook de pré-publicação da candidata `v0.1.0-rc.9`. Ele somente se
torna um asset operacional válido quando anexado, antes da publicação, à
release GitHub imutável da mesma tag e quando a imagem exata existir no GHCR.

O upgrade parte de `v0.1.0-rc.8`. Esta etapa publica e implanta o código, aplica
a migration aditiva e comprova que o catálogo v2 continua vigente. Ela não
executa dry-run nem publica o catálogo v3. A ativação permanece uma operação
posterior, explícita e restrita a futura meia-noite de `America/Bahia`.

## Resumo da release

A RC9 entrega:

- `occupancy-v3`, selecionável somente por catálogo temporal publicado;
- normalização transversal de posição física por setor-fonte e leito;
- colapso de duplicatas exatas sem deduplicar prontuários em leitos distintos;
- conflito ou posição ocupada sem identidade excluídos do numerador, com taxa
  parcial e inelegibilidade diária;
- reconciliação histórica agregada, allowlisted e sem dados identificáveis;
- disponibilidade oficial calculada e somada por setor, sem compensação de
  excedentes entre unidades;
- separação de `/beds` entre `Capacidade oficial e ocupação` e `Posições
  registradas no sistema legado`;
- compatibilidade imutável com medições `occupancy-v1` e `occupancy-v2`;
- ADR-0005 para identidade física, deduplicação, conflito, disponibilidade e
  apresentação das duas realidades.

A release não altera capacidade 666, política do Centro Obstétrico, partição
Adulto/Infantil da 3A, autenticação ou fluxo clínico. Não faz backfill, não
corrige snapshots brutos e não ativa v3 durante build, migration ou deploy.

## Backup obrigatório

Com somente o banco ativo:

```bash
mkdir -p /srv/apps/prisma/backups
chmod 700 /srv/apps/prisma/backups
export BACKUP_FILE="/srv/apps/prisma/backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f compose.hospital.yml exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  > "${BACKUP_FILE}"
test -s "${BACKUP_FILE}"
sha256sum "${BACKUP_FILE}" > "${BACKUP_FILE}.sha256"
chmod 600 "${BACKUP_FILE}" "${BACKUP_FILE}.sha256"
sha256sum -c "${BACKUP_FILE}.sha256"
stat -c '%a %n' /srv/apps/prisma/backups \
  "${BACKUP_FILE}" "${BACKUP_FILE}.sha256"
```

Não copie o backup para o repositório, release ou diretório público.

## Rollback antes da ativação v3

A migration `0021` pode permanecer porque é aditiva. Para rollback funcional,
pare serviços mutantes, restaure o Compose RC8 preservado, selecione
`SIRHOSP_VERSION=v0.1.0-rc.8`, faça pull e retome a topologia com dez workers.
Não reverta migrations nem restaure o backup apenas para rollback funcional.

Depois que um catálogo v3 futuro for publicado, versões antigas não devem
materializar censos a partir da sua vigência. A estratégia preferencial passa a
ser correção forward.
