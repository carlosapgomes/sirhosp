# Runbook de upgrade — v0.1.0-rc.48

Upgrade hospitalar da `v0.1.0-rc.47` para a `v0.1.0-rc.48` (performance da
página de métricas de ingestão + índices concorrentes).

## Escopo

- `12494ec`–`91f0fbd` — performance de `/metrica-ingestao/` (change OpenSpec
  `ingestion-metrics-page-performance`, IRMPP-S1 a S4 aceitos): computação
  lazy por aba/modo (fim das ~187 queries/abertura), histórico de batches
  leve (colunas baratas + 1 agregação SQL por página), métricas caras de
  eficiência movidas para o bloco de detalhe do batch selecionado e
  paginação elidida com `flex-wrap`. Detalhes e evidências:
  `2026-11-08_v0.1.0-rc.48.md`.
- Migration `ingestion.0007_add_finished_at_indexes`: btree em
  `IngestionRun.finished_at` e `CensusExecutionBatch.finished_at` via
  `AddIndexConcurrently` (`atomic = False`; primeiro uso no repo).
- `e6cea77` — archive/sync OpenSpec; sem impacto de runtime.
- Sem mudanças em `compose.hospital.yml`, units systemd, scripts de deploy ou
  variáveis de ambiente.

## Impacto operacional

- Release de código **com migration aditiva de índices**: `migrate --noinput`
  **não é no-op** nesta release e deve aplicar exatamente
  `ingestion.0007_add_finished_at_indexes` (nenhuma outra app).
- A criação é `CREATE INDEX CONCURRENTLY`: **não segura lock de escrita**
  prolongado nas tabelas grandes (`ingestionrun` ~2,1 M de linhas), mas o
  build demora mais que um índice comum — deixe o `migrate` concluir sem
  interromper (minutos, não segundos). Se o build for interrompido, o
  PostgreSQL deixa índice **INVALID** que bloqueia re-execução: confira a
  seção Validação (índices devem estar `indisvalid = t`) e, se necessário,
  faça `DROP INDEX CONCURRENTLY` do índice inválido antes de re-rodar o
  `migrate`.
- Página de uso **admin/técnico** (`/metrica-ingestao/`): sem mudança clínica
  e sem mudança de conteúdo visível por aba; a diferença visível é o
  carregamento (~4 s → sub-secondário por aba) e a paginação elidida
  (transbordamento horizontal resolvido). As métricas de eficiência
  (workers, pico, jobs/min) agora aparecem no detalhe do batch (`?batch_id=`).
- Assets de runtime byte a byte idênticos aos das rc.34–rc.47 (Compose
  `cd0e444c…`). Nenhuma variável de ambiente, serviço ou timer novo.
- Rollback por imagem para a rc.47 (totalmente funcional): não desfaça a
  migration nem restaure o banco; os índices extras são inócuos para a rc.47
  (continuam válidos e até aceleram ordenações por `finished_at`).

## Pré-condições

1. Confirmar versão atual `v0.1.0-rc.47` e PostgreSQL saudável.
2. Parar produtores e drenar até `drain_state=0 0`:

   ```bash
   systemctl stop sirhosp-stale-reconciliation.timer
   docker compose --env-file .env -f compose.hospital.yml stop census_orchestrator
   drain_state="$(
     docker compose --env-file .env -f compose.hospital.yml exec -T web \
       uv run --no-sync python -c \
       'import os,django; os.environ.setdefault("DJANGO_SETTINGS_MODULE","config.settings"); django.setup(); from apps.ingestion.models import IngestionRun,CensusExecutionBatch; print(IngestionRun.objects.filter(status__in=("queued","running")).count(), CensusExecutionBatch.objects.filter(status="running").count())'
   )"
   printf 'drain_state=%s\n' "$drain_state"
   test "$drain_state" = "0 0"
   ```

3. Baixar assets da release imutável rc.48 (Compose `cd0e444c…`).
4. Backup PostgreSQL custom + `pg_restore --list`.

## Download e backup

```bash
set -euo pipefail
export OLD_VERSION=v0.1.0-rc.47
export NEW_VERSION=v0.1.0-rc.48
export COMPOSE_FILE=compose.hospital.yml
cd /srv/apps/prisma
curl -fL --retry 3 -o "${NEW_VERSION}-upgrade.md.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${NEW_VERSION}-upgrade.md"
curl -fL --retry 3 -o "${COMPOSE_FILE}.new" \
  "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${COMPOSE_FILE}"
for unit in sirhosp-discharges.service sirhosp-discharges.timer \
  sirhosp-historical-recovery.service sirhosp-historical-recovery.timer \
  sirhosp-stale-reconciliation.service sirhosp-stale-reconciliation.timer \
  sirhosp-daily-statistics.service sirhosp-daily-statistics.timer; do
  curl -fL --retry 3 -o "deploy/systemd/${unit}" \
    "https://github.com/carlosapgomes/sirhosp/releases/download/${NEW_VERSION}/${unit}"
done
sha256sum "${COMPOSE_FILE}.new"   # cd0e444c…
cp -p "$COMPOSE_FILE" "${COMPOSE_FILE}.${OLD_VERSION}"
mv "${NEW_VERSION}-upgrade.md.new" "${NEW_VERSION}-upgrade.md"

backup_path="backups/sirhosp-$(date -u +%Y%m%dT%H%M%SZ).dump"
docker compose --env-file .env -f $COMPOSE_FILE exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > "${backup_path}"
test -s "${backup_path}"
docker compose --env-file .env -f $COMPOSE_FILE exec -T db pg_restore --list < "${backup_path}" >/dev/null
echo "backup=${backup_path}"
```

## Upgrade

> `docker compose up -d` **sempre direto na linha de comando** (fora de
> heredoc) e com confirmação explícita das imagens. Não interrompa o
> `migrate` durante o build dos índices concorrentes.

```bash
umask 077
sed "s/^SIRHOSP_VERSION=.*/SIRHOSP_VERSION=${NEW_VERSION}/" .env > .env.new
grep -n "^SIRHOSP_VERSION=${NEW_VERSION}$" .env.new
chmod 600 .env.new && mv .env.new .env
mv ${COMPOSE_FILE}.new $COMPOSE_FILE
docker compose --env-file .env -f $COMPOSE_FILE config --quiet
docker compose --env-file .env -f $COMPOSE_FILE pull
docker compose --env-file .env -f $COMPOSE_FILE run --rm web \
  uv run --no-sync python manage.py migrate --noinput
```

Critério do `migrate`: exatamente `ingestion.0007_add_finished_at_indexes...
OK` e nenhuma outra migration. A etapa pode levar alguns minutos (build
concorrente sobre ~2,1 M de linhas).

Direto na linha de comando:

```bash
docker compose --env-file .env -f compose.hospital.yml up -d --remove-orphans \
  --scale persistent_worker=10 db web persistent_worker summary_worker
install -m 0644 deploy/systemd/*.service deploy/systemd/*.timer /etc/systemd/system/
systemctl daemon-reload
docker compose --env-file .env -f compose.hospital.yml ps --format '{{.Name}} {{.Image}}' | sort
```

Critério: 12 containers na imagem rc.48 (web, summary_worker e 10
persistent_workers; o db permanece a imagem do PostgreSQL).

## Rollback

Somente imagem: a rc.47 está totalmente funcional. Não desfaça
`ingestion.0007` nem restaure o banco; os índices `finished_at` permanecem
válidos e inócuos para a rc.47. Pare produtores, drene, troque
`SIRHOSP_VERSION=v0.1.0-rc.47` e recrie os containers (mesmos passos acima;
o `migrate` da rc.47 é no-op).
